## 一、为什么这节课重要：Prompt 已经是新的“编程接口”

这份讲义反复强调一个核心判断：

- Prompt 不只是“和模型聊天”的一句话，而是你驱动模型行为的**接口语言（lingua franca）**；
- 在编程语言演化路径里，Prompting 可以被看作“下一层抽象”；
- 你不仅要会“对 AI 提需求”，还要理解 Cursor / Claude Code 一类工具背后的机制——它们本质上都叠了大量 Prompt 策略。

换句话说，Prompting 的价值有两层：

1. **直接生产力**：让你更快得到可用结果；
2. **系统理解力**：理解现代 AI 编程工具为什么有时“神准”、有时“翻车”。

讲义还给了一个很好的类比：

- 过去搜索引擎查询偏“布尔表达式式”；
- 现在越来越自然语言化；
- Prompting 同样在走向“更自然、更结构化、更可组合”的阶段。

所以它既是艺术（black-box 经验），也是科学（可复用的实证技巧）。

## 二、课程主线：7 种核心 Prompt 技术

这节课的主体就是 7 种方法，从简单到复杂，基本覆盖今天 AI 编程的主流套路。

---

### 1）Zero-shot Prompting：先让模型“裸跑”

**定义**：不给示例，直接下达任务。
**特点**：低成本、启动快、适合试探。
**风险**：复杂任务下输出波动大。

讲义的示例（如“写 Rust for-loop”）说明：

- Zero-shot 很适合拿到第一版答案；
- 但如果涉及代码规范、风格、复杂推理，往往不够稳定。

**实战建议**：
- 用 Zero-shot 作为 baseline（基线）；
- 不要期待它一次解决高约束任务。

---

### 2）K-shot Prompting：给示例，让模型学“你这套规矩”

**定义**：在 prompt 里放入 k 个示例（常见 1/3/5），引导模型按样式输出。
**别名**：In-context Learning（上下文学习）。

讲义给出的关键点非常实用：

- **特别适合**：
  - 企业私有 API / 内部 DSL；
  - 你希望严格统一命名、格式、代码风格。
- **不适合**：
  - 通用库上的普通任务（模型本来就会）；
  - 给太多示例导致过约束或噪声增大。

这其实回答了很多人的困惑：

> “为什么我给了很多例子，结果反而变差？”

因为示例不是越多越好，而是要“少而精、覆盖关键模式”。

---

### 3）Chain-of-Thought（CoT）：把推理过程显式化

**定义**：要求模型按步骤思考并输出中间推理。
**两类常见形式**：
- Multi-shot CoT：给推理示例；
- Zero-shot CoT：例如“Let’s think step-by-step”。

讲义明确指出 CoT 是很多推理模型的“工作马”。

**适用场景**：
- 编程问题拆解；
- 数学与逻辑链条较长的任务；
- 需要可解释过程的答案。

**讲义示例启发**：
- “判断完全立方且完全平方”；
- “最长递增子序列”；
这些任务都天然需要分步骤建模与验证。

---

### 4）Self-consistency：多次采样 + 多数投票

**定义**：同一个问题采样多次（通常搭配 CoT），汇总最一致答案。
**本质**：一种轻量“模型集成”思想。

讲义里用 `IndexError: list index out of range` 作为例子：

- 不是只问一次就认结果；
- 而是多次采样，让错误答案被“稀释”；
- 最终取主流一致结论，提升鲁棒性。

**它解决的核心问题**：
- LLM 的随机性导致“偶发翻车”；
- 一次命中的运气，不如统计上的稳定。

---

### 5）Tool Use：该查就查、该跑就跑

**定义**：允许模型调用外部工具（测试、检索、执行系统命令等）。
**价值**：
- 降低幻觉（用事实替代猜测）；
- 提升自治能力（从“会说”到“会做”）。

讲义示例很典型：

- “修复 IndexError 后，确保 CI 测试通过”；
- 给定可调用工具（例如 `pytest`）；
- 模型不再只是给“理论建议”，而是执行验证闭环。

这是现代 coding agent 的核心能力之一：

> 不是只生成代码，而是能调用环境完成任务。

---

### 6）RAG（检索增强生成）：让答案建立在上下文证据上

**定义**：在生成前先检索相关资料，把结果喂给模型。
**讲义给的四个价值**：
1. 不重训练也能更新知识；
2. 迭代更快；
3. 更容易附带引用与可解释性；
4. 降低幻觉。

讲义还点明：你在 Cursor / Windsurf 里使用 `@context`，本质就是 RAG。

示例场景（扩展 OAuth 逻辑并引用文档链接）说明：

- 编程任务经常依赖“外部真相”（框架文档、接口规范）；
- RAG 让模型依据证据回答，而非“凭记忆猜版本”。

---

### 7）Reflexion（自我反思）：把失败反馈并回提示词

**定义**：让模型先给答案，再对答案做批判、修正。
**典型二回合模板**：
- Turn 1：给出初稿；
- Turn 2：要求“是否正确？若不正确请解释并重试”。

讲义强调 Reflexion 是自治式 coding agent 的关键机制，也常被叫做 self-critique。

示例（`company_location` 处理 string/json 导致 `JSONDecodeError`）展示了真实工程闭环：

- 观察失败信号（测试/报错）；
- 反思根因与假设；
- 更新解法再验证。

这也是从“会答题”到“会迭代”的分水岭。

---

## 三、三类基础术语：System / User / Assistant

讲义补了一个很关键但常被忽略的基础：

1. **System prompt**
   - 系统级消息，常对用户不可见；
   - 定义角色、边界、风格、输出规则。

2. **User prompt**
   - 用户的任务请求；
   - 你平时写的大部分提示词都在这层。

3. **Assistant output**
   - 模型最终输出。

理解这三层叠加关系，你就能更好解释很多“同样问题、不同工具结果不同”的现象：

- 工具厂商往往在 system 层加了大量“护栏”和策略。

---

## 四、最佳实践：从“能用”到“稳定可复用”

讲义最后的最佳实践非常工程化，可直接落地：

### 1）先做 Prompt 改写迭代
- 用 Prompt Improver 一类工具或手工迭代；
- 不断把“模糊需求”改成“可执行说明”。

### 2）清晰优先
- 如果一个几乎无上下文的人看你的 prompt 都会困惑，模型更可能困惑。

### 3）善用角色提示（Role Prompting）
- 在 system 中定义角色、审查标准、输出形式；
- 角色不是“装饰”，是行为约束。

### 4）结构化输入
- 日志、报错、代码片段分块标记：
  - `<log>...</log>`
  - `<error>...</error>`
- 结构化会显著降低模型漏读关键证据的概率。

### 5）明确约束
- 指定语言、框架、库、版本、边界条件、性能/安全要求；
- 让模型“知道什么不能做”。

### 6）任务拆解（Decompose）
- 大任务拆小任务；
- 每步都可验证，减少一次性失败成本。

---

## 五、把这套方法映射到你的开发工作流

如果把讲义变成一套“可执行流水线”，推荐如下：

1. **Zero-shot**：快速拿 baseline。
2. **K-shot**：加入风格/格式示例，控制输出一致性。
3. **CoT**：给复杂问题加步骤推理。
4. **Self-consistency**：对关键结论多次采样投票。
5. **Tool Use / RAG**：接入真实工具和文档证据。
6. **Reflexion**：根据测试与报错反馈继续修正。

这就是现代 AI 编码实践的核心闭环：

> 生成 → 验证 → 反思 → 再生成。

---

## 六、这节课最值得记住的 5 句话

1. Prompt 是新的编程接口，不只是聊天。
2. 技巧要组合使用，而不是押注单一招式。
3. 没有验证的“答案”不算完成任务。
4. 外部工具与检索是减少幻觉的关键。
5. 反思机制让模型从“一次回答”升级为“持续改进”。

## 七、把 Week1 的 7 个作业文件当成“技术示例库”

下面把 `Assignments/week1` 里的 7 个作业相关文件，逐个对应到本讲义方法，帮助你把“概念”变成“可执行动作”。

### 示例 1：`k_shot_prompting.py`（K-shot 的最小闭环）

**文件目标**：让模型把 `httpstatus` 正确反转成 `sutatsptth`。
**对应技术**：K-shot + 输出约束。

这个作业本质是在训练你做两件事：

1. 给足够清晰的少量示例，让模型学会模式；
2. 用“Only output ...”这种硬约束减少格式噪声。

**关键启发**：
- K-shot 最重要的不是“多”，而是“准”；
- 样例应覆盖最容易出错的模式（这里就是把 `httpstatus` 当两个词拆开的问题）。

---

### 示例 2：`k_shot_prompting_iteration_log.md`（提示词迭代方法论）

**文件目标**：记录从低成功率到更稳定版本的迭代过程。
**对应技术**：Prompt 改进流程（失败样例驱动）。

这个文件虽不是执行脚本，但非常关键：它把“Prompting 是工程而非玄学”落到了纸面。

你能在这里看到典型迭代套路：
- 初版失败（模型误拆词）；
- 加逐字母示例仍不稳；
- 持续根据失败样本修正指令与示例。

**关键启发**：
- 失败样本是最有价值的训练数据；
- 记录迭代历史，能显著提高复盘效率与可迁移性。

---

### 示例 3：`chain_of_thought.py`（多步推理的标准入口）

**文件目标**：求 `3^{12345} mod 100`，并按 `Answer: <number>` 输出。
**对应技术**：CoT（step-by-step）+ 终答案格式化。

这个作业体现 CoT 的两个工程要点：

1. 允许模型展示推理过程；
2. 强制最终答案格式，便于程序抽取与校验。

**关键启发**：
- CoT 不等于“让模型多说”，而是让推理结构化；
- 输出规范（例如固定 `Answer:` 前缀）是自动评测的前提。

---

### 示例 4：`self_consistency_prompting.py`（从“单次正确”到“统计稳定”）

**文件目标**：解决路程文字题，并通过多次采样 + 多数票提高正确率。
**对应技术**：Self-consistency + CoT。

脚本会运行多次，提取每次 `Answer:`，最后做多数投票。

**关键启发**：
- 在温度较高、答案波动的任务中，多数投票常比“只信一次输出”稳得多；
- 这是最容易落地的“轻量集成策略”。

---

### 示例 5：`tool_calling.py`（让模型学会“调用而不是猜测”）

**文件目标**：让模型输出合法 JSON 工具调用，调用 `output_every_func_return_type` 并比对真实结果。
**对应技术**：Tool Use + 严格结构化协议。

这个作业把“工具调用”拆成了完整链条：

1. 模型只返回 JSON（工具名 + 参数）；
2. 程序解析 JSON；
3. 执行真实工具；
4. 和期望输出比较。

**关键启发**：
- 工具调用最怕格式漂移，所以 system prompt 必须非常硬；
- 真正可靠的 Agent，一定是“模型决策 + 程序执行 + 结果校验”的组合。

---

### 示例 6：`rag.py`（上下文检索决定答案上限）

**文件目标**：基于 `data/api_docs.txt` 文档写 `fetch_user_name`，并命中 `requests.get`、`X-API-Key` 等关键片段。
**对应技术**：RAG（检索上下文）+ 代码生成约束。

这个作业本质在练两件事：

1. 选对上下文（`YOUR_CONTEXT_PROVIDER`）；
2. 严格要求“仅依据上下文”生成代码。

**关键启发**：
- RAG 的核心不是“塞很多资料”，而是“给最相关资料”；
- 缺上下文时，模型很容易补全出“看似合理但并不存在”的 API 细节。

---

### 示例 7：`reflexion.py`（失败反馈驱动二次修正）

**文件目标**：先生成 `is_valid_password`，若测试失败，再把失败信息喂回模型做二次修复。
**对应技术**：Reflexion（self-critique）+ 测试反馈闭环。

这个作业的关键在 `your_build_reflexion_context`：

- 你要把“上一版代码 + 失败样例”整理成对模型可消费的反馈；
- 模型据此改写实现，再跑测试验证。

**关键启发**：
- Reflexion 的价值不在“再问一次”，而在“把具体失败证据结构化地喂回去”；
- 这是现代 coding agent 从 Demo 走向实战的关键能力。

## 八、用这 7 个示例总结一条 Week1 通关路线

你可以直接按这个顺序推进：

1. `k_shot_prompting.py`：先掌握“示例 + 输出约束”；
2. `k_shot_prompting_iteration_log.md`：建立迭代记录习惯；
3. `chain_of_thought.py`：学会让推理可读、可抽取；
4. `self_consistency_prompting.py`：学会提升稳定性；
5. `tool_calling.py`：学会调用工具并校验结果；
6. `rag.py`：学会上下文驱动生成；
7. `reflexion.py`：学会失败反馈闭环修复。

这 7 个示例其实正对应了现代 AI 开发的完整能力树：

> 指令设计 → 推理控制 → 稳定性增强 → 外部工具联动 → 知识注入 → 自我修正。
